# e-PTW: план проверки нагрузки (ориентир 100k DAU)

**Связь:** [TZ_e-PTW_Firebase_v1.0.md](./TZ_e-PTW_Firebase_v1.0.md) — разд. 14.  
**Реализация (k6 + мок):** [../e-ptw/README.md](../e-ptw/README.md).  
**Цель:** согласовать, *как* тестируем, а не подменить DAU «тестом из одного ноута на сотни тысяч RPS».

---

## 1. Что тестируем, что нет

| Можно | Осторожно / отдельно |
|--------|------------------------|
| HTTP-обёртки: Callable Functions, внешний BFF, REST-прослойка (если есть) | «Чистый» Firestore 100k параллельных клиентов **без** прод-проекта — риск квот и счёта |
| **Staging**-проект с теми же **правилами/индексами**, **анонимизированные** данные | Нагрузка **на production** — только **ограниченные** canary-окна по согласованию |
| K6, Artillery, Locust, Gatling | K6 = число *виртуальных пользователей*; не путать с *DAU* |

---

## 2. Рабочий коридор для 100k DAW (оценка пика)

- **DAW** = уникальные в сутки; **пик CCU** (одновременно) для B2B-контура часто **0,5–3%** DAW, пока нет факт-метрик.
- При **100k DAW** **CCU (порядок)** **500–3000**; целевой RPS/опс считать **от пикового 15–60 мин**, а не DAW/86400.
- **Профиль суток:** не равномерная линия — **смены** (утро пик, ночь минимум) + **час X** пика.

---

## 3. Сценарии (минимум)

1. **Создание** черновика НД (write + валидация).
2. **Переход** по цепочке: согласовать / отклонить (write + **аудит** + при необходимости уведомление).
3. **Список** нарядов (фильтр tenant, пагинация) — *частые reads*.
4. **Карточка** НД + (если реализовано) **вложения** Storage — *download*, не 100% параллель.

В каждом сценарии: зафиксировать **p95/p99** и % ошибок.

---

## 4. Этапы прогона (рекомендуемый порядок)

| Этап | Длительность | Назначение |
|------|----------------|------------|
| Smoke | 1–2 мин, мало VU | Сценарий жив, мониторинг работает |
| Load | ramp 5–20 мин + плато 20–40 мин | Достичь **целевого RPS** (из расчёта пика) |
| Stress | выше целевого RPS | Потолок, деградация предсказуема, нет **каскадного** падения |
| Soak | 2–4 ч на **75–100%** целевой нагрузки | Утечки, квоты, CF cold start, стабильность |

---

## 5. K6: сценарии в репозитории

Готовые скрипты (запуск после `brew install k6` и поднятия [мока `e-ptw/mock-server`](../e-ptw/README.md)):

- `e-ptw/loadtest/k6/health-stages.js` — только `GET /health`, ступенчатая нагрузка.  
- `e-ptw/loadtest/k6/nd-mixed.js` — health + список + создание + «согласование» (пути как у мока).  

Ниже — **обобщённый** шаблон; для staging подставьте `BASE_URL` и реальные `POST`-тела.

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate } from 'k6/metrics';

const errorRate = new Rate('errors');

export const options = {
  stages: [
    { duration: '2m',  target: 20 },  // разогрев
    { duration: '5m',  target: 100 },
    { duration: '20m', target: 200 },  // «плато» — подставьте VU от расчёта
    { duration: '2m',  target: 0 },
  ],
  thresholds: {
    http_req_duration: ['p(95)<800'],
    errors: ['rate<0.01'],
  },
};

export default function () {
  const r = http.get('https://YOUR-STAGING.example.com/health', { timeout: '30s' });
  const ok = check(r, { '2xx': (r) => r.status >= 200 && r.status < 300 });
  errorRate.add(!ok);
  sleep(1);
}
```

**Для Firebase Callable** — тот же K6, но `POST` с **JSON** телом и **заголовками** (если бэкенд требует App Check / кастомный токен — **не** класть секреты в репозиторий, использовать **K6 `env` / secret store** в CI).

## 6. Метрики, которые смотрим в пик

- **Grafana / Cloud Monitoring / консоль Firebase:** CF invocations, memory, `timeout`, 5xx, Firestore **read/write** в минуту (если экспорт), **счёт** Blaze.
- **Клиент:** p95 TTI на экране списка, время до первой отрисовки после `snapshot`.

---

## 7. Критерий «прошли нагрузку» (пример, подставить цифры)

- В сценарии *load* на staging: p95 < **N** мс, ошибок < **0,5%**, **нет** устойчивого `RESOURCE_EXHAUSTED` / `Quota exceeded` при заявленном RPS.
- *Soak* 2+ ч без аномального роста **латентности** и **стоимости/час** (по плану).

---

## 8. Следующий шаг после пилота

- Заменить **допущения** (п.2) **факты**: DAW, **длина сессии**, события/сессию, реальный **пик** по дням недели — тогда **пересчитать** целевой RPS и **повторить** разд. 4.
