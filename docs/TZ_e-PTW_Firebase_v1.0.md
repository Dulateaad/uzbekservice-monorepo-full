# ТЕХНИЧЕСКОЕ ЗАДАНИЕ. Веб-приложение e-PTW (электронный наряд-допуск)

**Версия:** 1.1 (добавлен разд. 14 — DAU/нагрузка) | **Статус:** к согласованию

---

## 1. Назначение

Веб-приложение для оформления и согласования **наряда-допуска (НД)** на площадке: цепочка согласований, **подтверждение согласия** по согласованной модели (разд. 7), контроль срока, уведомления, учёт **документов/сертификатов** и **чек-листов** (в т.ч. **огневые работы** — галочки/пункты).

**Платформа:** **Firebase** — Auth, Firestore/RTDB, Storage, Cloud Functions, **FCM** (по необходимости). Состав сервисов согласуют ИТ/ИБ; **мультитенантность** — разд. 9.

---

## 2. Роли (минимум)

| Роль | Функции |
|------|--------|
| Инициатор | Создаёт НД, поля, вложения, чек-лист. В UI отображать, кто инициатор (по справочнику). |
| Согласующий 1…N | Согласует; подтверждение — разд. 7. |
| Проверяющий | Проверяет полноту/корректность; подтверждение — разд. 7. |
| Утверждающий | Финальное утверждение → статус **«Открыт»**. |
| Админ площадки (опц.) | Типы нарядов, шаблоны, маршруты, список лиц, допустимый к ролям. |

Роли **допускается сжать** до 2–3, если **сохранён** порядок этапов. **Справочник** сотрудников/должностей — **утверждённый** заказчиком перечень для выбора при назначении в наряды (кадры/договоры с подрядом — согласовать источник данных).

---

## 3. Happy path

1. Инициатор создаёт НД, указывает обязательные **документы, сертификаты, чек-лист** (огневые и т.д.).
2. **«На согласовании»** → уведомление следующему.
3. Согласующий: согласовано → подтверждение (разд. 7) → **аудит** (кто, когда, **версия** НД).
4. Проверяющий: проверка → подтверждение → аудит.
5. Утверждающий: **«Открыт»**.
6. **Срок 7 календарных дней.** **По умолчанию (пилот):** с момента **«Открыт»**. **Альтернатива:** с **даты начала работ** в карточке. **Окончательно** — разд. 10.
7. Уведомления: **наряд открыт**, **на сколько дней**, **дата окончания** действия.

---

## 4. MVP+ / релиз 1.x

- **Участники** НД: исполнители, наблюдатели, доп. согласующие — поля, **права, уведомления** (согласовываются).
- **Аннулирование** (кто: **утв./админ**), **обязательная причина**, **«Аннулирован»**, уведомления, аудит.
- **Продление:** после повторного согласования; мини-флоу или полный — **разд. 10**; **история** продлений.
- **Уведомления:** открытие, **за 1 сут. до** оконч. срока, аннул., продл., **откл./дораб.**

## 5. Отказ и доработка (бэклог по приоритету)

- **Отказ** — поле **«Причина отказа»**; **инициатору**; **«Отклонён»**; аудит.
- **Доработка** — **«Что исправить / причина»**; **инициатор**; **повтор** цепочки; **с какого шага** — **разд. 10**.

## 6. Вложения и чек-лист

- **Storage:** тип, кто загрузил, дата/время.
- **Чек-лист** по типу НД; **настраивает** админ площадки.
- **Версия файла** при замене: новая версия, **кто заменил**; **история** для **аудита**.

## 7. «Подпись» — фиксация для юристов, клиента, ИБ

*Раздел не заменяет индивидуальное юр. заключение; применимость электронной подписи (ЭП) и **ПДн/биометрии** — по **юрисдикции** и **договору**.*

**7.1. Варианты, из которых выбрать основной для MVP** (остальные — **дополнительно** по **заключению** юр. службы, как **фактор** усиления, не как обещание **КЭП**, если **КЭП** не внедрена):

- **ЭП/КЭП** (в РК — НУЦ РК, eGov Mobile, Kaztoken NFC — разд. 12.4), если норма/договор так требуют;
- **простая ЭП / явная** кнопка с текстом о **юридическом значении** действия + **аутентификация (пароль/2FA)**, по согласованию с юристом;
- **фото / Liveness / Face ID** на устройстве — только при оформлении требований к ПДн/био; для рынка РК с требованием ЭП (разд. 12.4) — как **дополнительный** фактор «кто у устройства», **не** как замена ЭЦП без отдельного утверждения юристом.

**7.2. Журнал аудита (обязателен):** пользователь, роль, время, действие, предыдущий статус → новый; идентификатор наряда и версии/события; по политике ИБ: IP, User-Agent; ссылка/идентификатор артефакта (в т.ч. фото) в Storage; при внедрении — хэш пакета данных на момент подписи (согласуется с заказчиком).

**7.3. Хранение фото/биометрии (если применяется):** категория данных, согласия, срок хранения, доступ, удаление/архив — отдельное приложение к ТЗ или политика заказчика (ПДн, ИБ).

## 8. OKR для площадки (пример на квартал)

**Цель:** наряды на площадке оформляются и ведутся в системе, без критичной выработки «живых» бумажных обходов.

| KR | Метрика | Целевое значение (заказчик) |
|----|---------|----------------------------|
| KR1 | Доля нарядов, полностью прошедших цепочку в приложении | ≥ X % |
| KR2 | Среднее/медианное время «создание → Открыт» | ≤ Y часов (p90 — отдельно) |
| KR3 | Снижение критичных инцидентов из-за просроченного/недействующего наряда | 0 или снижение на Z % |
| KR4 | Активные пользователи / площадки с ≥1 нарядом в неделю | N, M |

*X, Y, Z, N, M подставляются по базовой линии до пилота.*

## 9. B2B: документы и мультитенантность

**9.1. Документ для закупки/руководства (1–2 стр.).** Проблема: бумага, срывы сроков, нет прозрачности. Решение: единый цифровой наряд, цепочка, подтверждение (разд. 7), срок 7 дней (привязка — разд. 3 и 10), уведомления, аннулирование/продление, аудит. Безопасность: Firebase, роли, аудит (кратко). Пилот: 1 площадка, 4–8 недель, критерии — OKR (разд. 8).

**9.2. Техническое приложение (ИТ/ИБ):** схема данных в общих чертах, хранение файлов, перечень интеграций, резервное копирование, кто администрирует tenant (организация/площадка).

**9.3. Мультитенантность**

| Вариант | Суть | Плюсы | Риски |
|--------|------|-------|-------|
| A | Одна организация = один проект Firebase | Сильная изоляция | Стоимость, операции |
| B | Один проект, в данных companyId / siteId | Ниже совокупная стоимость | Жёсткие правила Firestore, тесты доступа |

**9.4. Коммерческая подача (ориентир):** пакеты «Площадка S / M / L», лимиты пользователей и нарядов, опция white-label, SLA поддержки — по договору.

## 12. Дополнения по анализу конкурентов (sPoint, GT Solution)

**12.1. Запрет двойного наряда [MVP, критично].** Системная проверка: у **производителя работ** (определение в справочнике) не может быть двух одновременно **действующих** «Открыт» НД при настройке запрета. Блок + ссылка на действующий НД. Обход — только админ/утв. с записью в аудит.

**12.2. Библиотека рисков и мер контроля [MVP, критично].** По типу работ — типовые риски, меры, СИЗ, ответственный; инициатор подтверждает и дополняет; в теле НД и в PDF (по договору). Настраивает админ.

**12.3. QR для верификации на месте [MVP, критично].** После утверждения — уникальный номер и QR; по скану: номер, статус, срок, кратко объём, подписи — без утечки лишних ПДн (политика ИБ).

**12.4. ЭЦП НУЦ РК (eGov Mobile, Kaztoken NFC) [MVP для сегмента РК / крупных заказчиков].** Рекомендация: ЭП по НУЦ — основной юридически значимый контур; Face ID/фото — доп. фактор, не замена ЭЦП без заключения юриста.

**12.5. Карта объекта и SIMOPS [MVP+].** Схема объекта, зоны, наложение активных НД, пересечения/параллельные работы — уведомления.

**12.6. Аналитика загруженности [MVP+].** Время согласования по ролям, очереди, просрочки, отчёты по подрядчикам (дополняет разд. 11).

**12.7. LOTO [1.x].** Блокировки энергии, статусы, связь с НД — по требованию отрасли/клиента.

**12.8. Lessons learned [1.x].** Подсказки по аналогичным работам/объекту, обяз. ознакомление в аудит.

**12.9. AI-ассистент черновиков [2.0].** Во внутреннем контуре, без утечки данных наружу.

## 13. Право и «законность» согласований (общая ориентация, не юр. консультация)

Законность **в смысле** применимых норм и договоров обычно опирается на: **кто** согласовал (**идентификация, полномочия**), **что** согласовано (**незыблимая** связь с **версией** НД и вложениями), **когда** и **в какой** последовательности (**аудит**), **неотказуемость** в практическом смысле (учётка, при необходимости 2FA, ЭП **по нормам** ЭДО).

| Подход | Смысл |
|--------|--------|
| Фото/селфи как единственная «подпись» | Часто **недостаточно** для внешней силы; чувствительны ПДн/био. |
| Роспись пальцем/стилусом (простая ЭП) | Сила **зависит** от процесса и закона, не от «красивости» линии. |
| КЭП/ЭП по НУЦ (РК) | **Максимальная устойчивость** там, где норма/заказчик так требуют. |

**Практика для площадки:** **учётка + роль + привязка к версии + время + аудит**; **КЭП** на **ключевых** шагах **по** **заключению** **юр.** **;** **фото** — **добавка**, **если** **политика** **и** **юрист** **утвердили**.

**Вопросы к юристу (чеклист):** достаточно ли **ПЭП+регламент**; где **нужна** **КЭП**; **статус** **селфи** **как** **био**; **текст** **кнопок** **«**Согласовать**»** **/ ** **подписи** **.**

## 14. Нефункциональные требования: нагрузка (ориентир **~100k DAU**)

*Раздел добавлен для планирования и приёмо-сдаточных испытаний; точные цифры **уточняются** после пилота (метрики реального использования).*

### 14.1. Термины

| Показатель | Смысл |
|------------|--------|
| **DAU** | Уникальные пользователи с ≥1 осмысленным действием за **сутки** (24 ч по часовому поясу площадки/tenant). |
| **Пик CCU** | Максимальное **одновременно** открытых сессий (оценка для ёмкости, не «равно DAU»). |
| **RPS** | Запросов к **HTTP/Callable API** в секунду; для Firestore — отдельно **read/s write/s** (в т.ч. за счёт `onSnapshot`). |

### 14.2. Допущения для **100k DAU** (рабочая модель для расчёта ёмкости)

1. **Нагрузка распределена по 24 ч**; пик **не** «вся база в одну минуту» — в тесте моделируют **суточный профиль** (смены: утро/день/вечер/ночь) и внутри него **час пика**.
2. **Пик CCU** (орден величины, до уточнения аналитикой): **0,5% … 3%** от DAU для B2B-приложения с сессиями 5–30 мин, т.е. **~500 … 3 000** одновременно при **100k DAU** (коридор; факт снимается метрикой **Firebase Analytics** / аналог + бэкенд-логи).
3. На одного пользователя в пике: **0,2…2 запроса/с** к API (усреднённо по пику), **чтения Firestore** выше — из‑за **листенеров** на списки нарядов/карточек; **записи** — в основном при согласовании, смене статуса, аудите.

*Интерпретация: **100k DAU** задаёт **суточный** объём событий; **ёмкость в RPS/ops** определяется **пиковым** окном 15–60 мин, а не делением DAU на 86 400.*

### 14.3. Что измерять (обязательно до «промышленного» масштаба)

- **Производительность:** p95 / p99 задержка клиента на ключевых сценариях (создать НД, открыть цепочку, согласовать, уведомление/открытие списка).
- **Надёжность:** доля 5xx / отменённых Cloud Functions; **идемпотентность** критичных write (дубликаты при повторе кнопки).
- **Бэкенд:** **Firestore** — read/write/удаления в секунду по коллекциям, **холодные/горячие** документы (избегать unbounded `onSnapshot` на «всю площадь»).
- **Стоимость/квоты:** панель **Firebase** + алерты по **Blaze** (лимиты, surprise traffic).

### 14.4. Как проверять (без иллюзий «100k VU в K6 = 100k DAU»)

| Этап | Содержание |
|------|------------|
| **A. База** | Нагрузочные тесты **на копии** (отдельный **Firebase**-проект *staging* или *emulator suite* + скрипты) — **не** первый бою на прод. |
| **B. Сценарий** | K6/Artillery/Locust: **ramp-up** в течение **5–20 мин** до **целевого RPS**, выдержка **20–40 мин** (*load*), отдельный прогон *stress* выше цели, *soak* **2…4 ч** (утечки, квоты, GC, CF). |
| **C. Суточный профиль** (опц.) | Несколько ступеней RPS за день (имитация смен) или **реплей** дневных логов. |
| **D. Критерий готовности** (пример) | В пике теста: p95 < **X** с, ошибок < **0,5%** (X согласовать); Firestore/CF без **sustained** throttling; бюджет **стоимости/день** в пределах **Y** (Y — по расчёту). |

*Готовый **репозиторий** с мок-API и сценариями: каталог [**`e-ptw/`**](../e-ptw/README.md) (K6 + `mock-server` без зависимостей).*

### 14.5. Проектные меры (Firebase)

- **Индексы** Firestore — по запросам списков/фильтров из разд. 11; без «скрытых» full scan.
- **Пагинация** и **ограничение** размера `where + orderBy + limit` по tenant/site.
- **Триггеры** CF — идемпотентность, **таймауты/память**, **очереди** (при пике уведомлений) — по необходимости.
- **Мульти-tenant (разд. 9.3):** `companyId` / `siteId` во **всех** правилах и запросах — обязателен для масштаба.

### 14.6. Ссылка на приёмку

NFR нагрузки **включается** в **протокол приёмки** пилота: целевые p95, допустимый % ошибок, **не превысить** согласованный **дневной/месячный** бюджет Firebase (отчёт в консоли + экспорт).
